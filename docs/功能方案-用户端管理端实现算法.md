## 2. 系统边界

### 2.1 用户端职责

用户端负责帮助用户完成以下决策和动作：

1. 找站
2. 比价
3. 看稳定性
4. 看风险
5. 自己测
6. 提交新站

### 2.2 管理端职责

管理端负责完成以下内部动作：

1. 收录和维护站点
2. 维护模型和官方价格
3. 抓取站点价格
4. 定时测试模型可用性和速度
5. 运行反造假规则
6. 审核公开提交
7. 处理误报和异常

## 6. 实现方案建议

## 6.1 总体架构

建议采用分层结构，而不是把前端、接口、抓取和测试全部塞进一个进程：

1. Web 前端
2. API 服务
3. Worker 任务服务
4. PostgreSQL 数据库
5. Redis 队列与缓存
6. 对象存储 / 文件存储

推荐逻辑架构：

1. `web`
   - 用户端页面
   - 管理端页面
   - SSR/SEO

2. `api`
   - 站点、模型、报价、排行、测试、风险、提交等接口

3. `worker`
   - 价格抓取任务
   - 定时测试任务
   - 风险分析任务
   - 第三方榜单同步任务

4. `db`
   - 结构化数据

5. `redis`
   - 任务队列
   - 排行缓存
   - 限流

6. `storage`
   - 风险证据原始数据
   - 抓取快照
   - 测试日志片段

---

## 6.2 推荐技术栈

### 前端

建议方案：

1. `Next.js`
2. `React`
3. `TypeScript`
4. `ECharts` 或 `Recharts`

原因：

1. 榜单、详情页、筛选页适合 SSR 和 SEO
2. 前后台可以共用组件和设计变量
3. 方便直接承接当前静态原型

### 后端 API

建议方案：

1. `NestJS` 或 `Fastify + TypeScript`

建议优先：

- `NestJS`

原因：

1. 模块边界清晰
2. 适合任务型系统拆分
3. DTO、校验、调度、依赖注入更规范

### 数据库与队列

1. `PostgreSQL`
2. `Redis`
3. `BullMQ`

原因：

1. 结构化关系数据多
2. 排行和聚合需要较强查询能力
3. 抓取、测试、风险分析适合队列化

### 抓取与测试

1. 抓取：`Playwright` + `HTTP 抓取器`
2. 测试：独立 `Worker`
3. 风险分析：规则引擎 + 批处理

## 6.5 数据流

推荐主链路如下：

1. 收录或审核通过站点
2. 初始化站点、模型、抓取规则
3. 定时抓取价格
4. 结构化生成 `RelayOffer`
5. 定时测试生成 `TestRecord`
6. 风险分析生成风险分和证据
7. 聚合生成排行和站点评分
8. 前台读取聚合结果

用户自助测试是另一条单独链路：

1. 用户输入站点地址、Key、模型
2. 生成临时测试任务
3. Worker 执行真实请求
4. 返回结果给当前用户
5. 默认不纳入公共排行

建议：

- 用户自助测试结果只对当前发起者可见
- 公共排行只使用平台定时测试数据

## 7. 核心算法设计

## 7.1 实际折算价

### 目标

解决“站点标价便宜，但充值比例或赠送规则导致实际并不便宜”的问题。

### 变量定义

- `site_unit_price`
  - 站点对某模型标注的价格
  - 单位通常是站内额度 / 1M tokens

- `paid_amount_local`
  - 用户实际支付金额

- `fx_rate`
  - 支付币种到 USD 的汇率

- `usable_credit`
  - 实际可用站内额度

### 建议计算

1. `paid_amount_usd = paid_amount_local / fx_rate`
2. `cost_per_credit_usd = paid_amount_usd / usable_credit`
3. `effective_price_usd = site_unit_price * cost_per_credit_usd`

### 示例

如果：

1. 用户支付 `100 CNY`
2. 汇率 `7.2`
3. 支付折合 `13.89 USD`
4. 站点实际给 `100` 点额度，外加赠送 `20` 点
5. `usable_credit = 120`
6. 模型标价 `3 点 / 1M`

则：

1. `cost_per_credit_usd = 13.89 / 120 = 0.11575`
2. `effective_price_usd = 3 * 0.11575 = 0.34725`

这个值才是前台比价应使用的主价格。

---

## 7.2 可用性

### 目标

衡量“这个站在某时间窗口内是不是经常能成功返回”。

### 建议公式

`availability(window) = success_count / total_count`

### 说明

1. 只统计平台定时测试
2. 按模型维度计算
3. 同时保留：
   - 24h 可用性
   - 7d 可用性
   - 30d 可用性

---

## 7.3 稳定性

### 目标

衡量“不是偶尔成功，而是连续稳定”。

### 输入

1. 成功率
2. 首 token 时间波动
3. 完整响应耗时波动

### 建议公式

先定义：

1. `availability_rate = success_count / total_count`
2. `ft_cv = std(first_token_time) / mean(first_token_time)`
3. `rt_cv = std(response_time) / mean(response_time)`

再归一化：

1. `ft_stability = 1 - min(ft_cv, 1)`
2. `rt_stability = 1 - min(rt_cv, 1)`

最终：

`stability_score = 100 * (0.6 * availability_rate + 0.2 * ft_stability + 0.2 * rt_stability)`

### 解释

1. 成功率仍然是稳定性的主体
2. 速度波动越小，稳定性越高
3. 该分值适合做 7d 和 30d 排行

---

## 7.4 速度评分

### 目标

把“首 token 快”和“完整响应快”合并成一个便于排序的分数。

### 输入

1. `first_token_time`
2. `full_response_time`

### 建议做法

按同一模型下所有站点做分位归一化：

1. `ft_score`
2. `rt_score`

然后：

`speed_score = 100 * (0.6 * ft_score + 0.4 * rt_score)`

### 解释

1. 首 token 时间更影响用户主观体感
2. 完整响应耗时对长输出场景也重要

---

## 7.5 综合性价比评分

### 目标

给用户一个“不是单纯最便宜，而是整体更值”的排序。

### 建议公式

先定义：

1. `price_score`
   - 实际折算价越低越高分

2. `availability_score`
   - 基于 24h 或 7d 可用性

3. `stability_score`
   - 见上

4. `speed_score`
   - 见上

5. `safety_score = 100 - risk_score`

最终：

`value_score = 0.30 * price_score + 0.25 * availability_score + 0.20 * stability_score + 0.10 * speed_score + 0.15 * safety_score`

### 说明

1. 这是建议初版权重
2. 正式实现时应做成可配置
3. 对不同用户类型可扩展不同权重模板

---

## 7.6 站点整体评分

### 目标

从中转站整体角度衡量平台收录质量，而不是只看单一模型。

### 输入项

1. 站点支持模型数量
2. 平均价格竞争力
3. 平均可用性
4. 平均稳定性
5. 平均安全性
6. 企业属性完整度
7. 存活时长

### 建议公式

`site_score = 0.15 * model_coverage_score + 0.20 * avg_price_score + 0.20 * avg_availability_score + 0.20 * avg_stability_score + 0.15 * avg_safety_score + 0.10 * enterprise_score`

### 说明

1. `enterprise_score` 可以由开票、退款、文档、客服等字段组成
2. 存活时长可并入 `enterprise_score` 或作为独立加分项

---

## 7.7 风险分

### 目标

把多个风险规则统一成一个用户可以理解、后台可以追踪的分值。

### 建议范围

`0 - 100`

### 分段建议

1. `0-20`
   - 低风险
2. `21-50`
   - 中风险
3. `51-80`
   - 高风险
4. `81-100`
   - 严重可疑

### 建议计算方式

`risk_score = min(100, sum(rule_hit_score_i))`

即：

1. 每条规则独立给分
2. 多条规则命中累加
3. 最终封顶 100

---

## 7.8 风险规则设计

## 7.8.1 缓存假响应

### 检测思路

1. 使用带随机种子的测试题
2. 连续多次请求同一模型
3. 如果理论上应变化的输出高度一致，则提升风险分

### 建议加分

`15 - 30`

---

## 7.8.2 模型偷换

### 检测思路

1. 针对目标模型维护一组能力指纹题
2. 对输出做规则化评估
3. 与目标模型基线差异过大时提升风险分

### 建议加分

`20 - 40`

---

## 7.8.3 降级模型冒充高阶模型

### 检测思路

1. 选取能拉开模型档次的题集
2. 观察推理、代码、结构化输出等结果
3. 连续多次明显低于目标模型预期时判为高风险

### 建议加分

`25 - 45`

---

## 7.8.4 价格虚标

### 检测思路

1. 对比站点展示价格和抓取价格
2. 如果有内部测试账号，再对比实际扣费结果
3. 若长期不一致，计入风险

### 建议加分

`10 - 25`

---

## 7.8.5 响应伪造

### 检测思路

1. 检查响应结构是否异常
2. 检查 usage、角色、格式是否长期固定得不合理
3. 检查延迟与输出长度是否出现不可能组合

### 建议加分

`15 - 35`

---

## 7.9 排行刷新策略

### 建议策略

1. 每小时测试批次结束后重新聚合
2. 价格抓取完成后重算相关模型价格榜
3. 风险分变化后同步刷新受影响站点和模型排行

### 建议实现

1. 原始记录表保留明细
2. 聚合结果表单独存储
3. 前台优先读聚合表，避免实时大查询

## 10. 当前建议结论

这个项目不是资讯站，也不是单纯导航站，而是一个：

1. 用数据做中转站收录
2. 用统一价格做横向比价
3. 用定时测试做稳定性判断
4. 用规则和证据做反造假

首期真正的竞争力不在页面数量，而在以下三点：

1. `实际折算价` 算得准不准
2. `平台定时测试` 跑得稳不稳
3. `风险分 + 证据记录` 能不能让用户信服

如果这三点成立，排行榜和流量入口才有价值。

# 中转站模型有效性自动测试方案

## 1. 文档目标

本文档定义“系统自动测试中转站模型是否有效”的落地方案，目标是让平台能够基于真实 API 探测，持续、自动、可解释地判断：

1. 某个中转站上的某个模型是否真的可调用。
2. 调用是否符合 OpenAI Chat Completions 兼容协议。
3. 调用是否具备基本可用性，而不是只有 HTTP 200 的假成功。
4. 异常是短时抖动还是持续性失效。

本文档只聚焦“模型有效性自动测试”，不覆盖价格抓取、排行榜展示、复杂模型指纹识别和扣费真实性核验。

---

## 2. 参考依据

本方案主要基于以下资料整理：

1. `https://llm.ztest.cc/methodology`
2. 项目现有文档《AI 中转站模型测试方案》
3. 项目现有文档《中转测试真实检测开发文档》

其中 methodology 页的核心约束有三条，本文直接继承：

1. 只做真实 API 请求探测，不做假的连通性冒烟。
2. 仅 HTTP 200 不算成功，必须收到至少 1 个有效流式 delta。
3. 状态判定需要防误报，不能因为一次瞬时失败就直接判定失效。

---

## 3. 有效性的定义

对“中转站模型有效”统一定义如下：

1. 目标地址可访问。
2. 使用指定 API Key 与模型名可以发起真实聊天请求。
3. 返回内容符合 OpenAI Chat Completions 兼容结构，或符合 SSE 流式输出结构。
4. 在超时时间内收到至少 1 个有效 token 增量。
5. 响应能够正常结束，而不是空流、假流、截断流或结构伪造。

满足以上条件，单次探测记为 `valid`。

以下情况视为单次无效：

1. 连接失败、TLS 失败、DNS 失败。
2. HTTP 401 / 403 / 404 / 429 / 5xx。
3. 模型不存在或模型路由不可达。
4. 返回了 HTTP 200，但没有任何有效 delta。
5. 返回内容不是合法 JSON 或合法 SSE 事件流。
6. 响应超时、中断或内容为空。

---

## 4. 设计原则

## 4.1 真实请求原则

系统必须对真实中转站、真实模型名、真实凭据发起探测。禁止只做以下伪检测：

1. 仅检查域名可访问。
2. 仅检查 `/v1/models` 返回正常。
3. 仅检查 TCP/HTTP 建连成功。

原因是这些检测无法证明“这个模型真的能用”。

## 4.2 固定探测口径原则

平台自动测试必须使用统一的探测参数，避免结果不可比：

1. 固定请求结构。
2. 固定 prompt 模板。
3. 固定 `max_tokens` 上限。
4. 固定温度或随机性设置。
5. 固定超时与重试策略。

## 4.3 轻量低扰动原则

探测请求应尽可能短，目标是验证有效性，而不是消耗额度做能力评测。单次请求只做最小必要验证：

1. 是否能返回有效内容。
2. 是否符合协议。
3. 是否能在合理时间内输出。

## 4.4 证据可回放原则

系统必须保存足够证据，确保后续可以解释为什么判定有效或无效，但不保存敏感明文：

1. 保留结构化摘要。
2. 保留错误分类。
3. 保留耗时指标。
4. 保留响应片段摘要。
5. 不保留 API Key 明文。

## 4.5 防误报原则

单次失败不直接判定站点模型失效。必须通过状态机和补测策略降低误报。

---

## 5. 测试对象

自动测试的最小对象定义为：

`relay_site + channel + model`

说明：

1. 同一中转站不同渠道要分开测试。
2. 同一渠道下不同模型要分开测试。
3. 同一模型在不同地区代理出口下，如后续有需要，可扩展为独立监测对象。

---

## 6. 探测请求规范

## 6.1 请求接口

统一使用 OpenAI Chat Completions 兼容接口：

`POST /v1/chat/completions`

若录入地址为 `/v1` 或完整 completions 地址，系统在执行前统一归一化。

## 6.2 请求参数

建议默认参数如下：

```json
{
  "model": "{{modelName}}",
  "stream": true,
  "temperature": 0,
  "max_tokens": 32,
  "messages": [
    {
      "role": "user",
      "content": "Reply with JSON only: {\"ok\": true, \"echo\": \"cheapai\"}"
    }
  ]
}
```

约束说明：

1. `stream` 必须为 `true`，用于验证真实流式返回。
2. `temperature` 固定为 `0`，减少结果波动。
3. `max_tokens` 保持较小，降低探测成本。
4. prompt 必须要求结构化短输出，便于解析。

## 6.3 超时策略

建议拆分两个超时：

1. 首 token 超时：`10s`
2. 总响应超时：`30s`

若首 token 未在 10 秒内到达，记为 `timeout_first_token`。
若流未在 30 秒内结束，记为 `timeout_full_response`。

## 6.4 重试策略

默认策略：

1. 首次失败后重试 2 次。
2. 每次重试间隔 500ms。
3. 同一轮探测仅在网络类失败和超时类失败时重试。

以下错误不重试：

1. `401/403`
2. `model_not_found`
3. `invalid_request`

---

## 7. 成功判定规则

单次探测必须同时满足以下条件，才记为成功：

1. HTTP 状态码为 `200`。
2. 响应可被识别为合法 SSE 或合法 JSON 完整包。
3. 至少收到 1 个有效 `delta.content` 或完整 `message.content`。
4. 内容非空。
5. 流正常结束，或完整包结构完整。

建议附加校验：

1. `choices` 数组存在。
2. `finish_reason` 字段存在或可推断结束。
3. 返回内容可解析为预期 JSON，若不能解析则记为协议部分失败。

### 7.1 假成功识别

以下情况必须明确记为失败，而不是成功：

1. HTTP 200，但没有任何 token。
2. 只有 SSE 框架事件，没有有效 `delta` 内容。
3. 只有错误模板文本，没有标准结构。
4. 返回内容为空字符串。
5. 首包即结束，没有实际输出。

---

## 8. 失败分类规则

失败类型统一枚举如下：

1. `network`
2. `dns_error`
3. `tls_error`
4. `timeout_first_token`
5. `timeout_full_response`
6. `http_4xx`
7. `http_5xx`
8. `auth_failed`
9. `rate_limited`
10. `model_not_found`
11. `empty_stream`
12. `invalid_sse`
13. `invalid_json`
14. `empty_content`
15. `content_filtered`
16. `unknown`

映射建议：

1. `401/403` 映射为 `auth_failed`
2. `404` 且模型相关报错映射为 `model_not_found`
3. `429` 映射为 `rate_limited`
4. HTTP 200 但无 delta 映射为 `empty_stream`

---

## 9. 状态机设计

为了避免偶发故障引发误判，自动测试状态分为 3 档：

1. `UP`
2. `DEGRADED`
3. `DOWN`

状态规则如下：

### 9.1 UP

满足以下条件：

1. 最近一次探测成功。
2. 首 token 时间 `< 5s`。
3. 最近两次探测中失败次数为 `0`。

### 9.2 DEGRADED

满足任一条件：

1. 探测成功，但首 token 时间 `>= 5s`。
2. 最近一次成功，但最近 3 次内存在 1 次失败。
3. 协议结构可用，但存在内容结构轻微异常。

### 9.3 DOWN

满足任一条件：

1. 连续 2 次探测失败。
2. 连续 2 次出现 `empty_stream`、`invalid_json` 或 `invalid_sse`。
3. 连续 2 次 `timeout_first_token` 或 `timeout_full_response`。

### 9.4 恢复规则

1. `DOWN -> UP`：1 次成功即可恢复，但若首 token 超过阈值，则先恢复到 `DEGRADED`。
2. `DEGRADED -> UP`：连续 2 次成功且耗时恢复正常。

---

## 10. 自动测试调度方案

## 10.1 基础探测频率

建议默认每 `5 分钟` 对每个监测对象执行一次轻量探测。

说明：

1. 该频率直接继承 methodology 页的监测思路。
2. 每次探测应带随机 `jitter`，避免分钟级同时打满所有站点。

建议 jitter：

1. 在当前 5 分钟窗口内随机延迟 `0-60s`。

## 10.2 补测策略

以下情况触发补测：

1. 单次失败。
2. 单次出现 `empty_stream`。
3. 单次出现 `invalid_json` 或 `invalid_sse`。
4. 单次首 token 超过 `10s`。

补测规则：

1. 失败后 `1 分钟` 内补测 1 次。
2. 若补测仍失败，再于 `5 分钟` 后补测 1 次。
3. 仅当连续失败达到阈值，才升级为 `DOWN`。

## 10.3 冷启动策略

新加入监测对象时：

1. 前 3 个有效样本仅显示“样本积累中”。
2. 在有效样本 `< 3` 时，不计算综合有效性分。

---

## 11. 评分设计

本方案不做复杂真假模型识别评分，只输出“有效性分”，用于系统判断与后台排序。

## 11.1 单次探测得分

单次探测满分 `100`：

1. 协议成功：40 分
2. 有效 delta：30 分
3. 内容非空且结构正确：20 分
4. 首 token `< 5s`：10 分

判定：

1. `>= 90`：有效
2. `70-89`：降级可用
3. `< 70`：无效

## 11.2 窗口期有效性分

对最近 24 小时数据按以下方式聚合：

`validity_score = 0.6 × success_rate + 0.2 × latency_score + 0.2 × stability_score`

字段定义：

1. `success_rate = 成功次数 / 总次数`
2. `latency_score = max(0, 1 - p95_first_token / 10)`
3. `stability_score = 1 / (1 + 状态翻转次数 / √样本数)`

最终结果乘以 `100` 输出为整数分。

## 11.3 样本保护

当最近窗口有效样本数 `< 3` 时：

1. `validity_score` 不显示数值。
2. 状态只显示最近探测结果，不参与公共排序。

---

## 12. 数据记录要求

每次探测至少记录以下字段：

1. `site_id`
2. `channel_id`
3. `model_id`
4. `probe_started_at`
5. `probe_finished_at`
6. `http_status`
7. `probe_status`
8. `failure_type`
9. `first_token_ms`
10. `full_response_ms`
11. `token_count_estimated`
12. `received_delta_count`
13. `response_excerpt`
14. `protocol_ok`
15. `content_non_empty`
16. `score`
17. `state_before`
18. `state_after`
19. `retry_count`
20. `config_version`

安全约束：

1. 不记录 API Key 明文。
2. 不记录完整原始响应全文。
3. 响应摘要仅保留前 200 到 500 个字符。
4. 涉及用户自助测试的数据不进入公共聚合。

---

## 13. 判定流程

系统执行顺序建议如下：

1. 读取监测配置。
2. 归一化 endpoint。
3. 发起真实流式请求。
4. 记录建连时间、首 token 时间、总耗时。
5. 校验 SSE/JSON 结构。
6. 校验是否收到有效 delta。
7. 归类失败类型。
8. 计算单次得分。
9. 更新状态机。
10. 如命中补测条件，则写入补测任务。
11. 刷新最近 24h 聚合结果。

---

## 14. 告警规则

建议只对持续性问题告警，不对单次波动告警。

### 14.1 触发条件

1. 连续 2 次失败，触发 `DOWN` 告警。
2. 最近 30 分钟成功率 `< 50%`，触发高优先级告警。
3. 最近 1 小时连续出现 `empty_stream` 3 次，触发协议异常告警。
4. 最近 1 小时 `p95_first_token > 10s`，触发性能退化告警。

### 14.2 告警内容

1. 站点名
2. 渠道名
3. 模型名
4. 当前状态
5. 最近失败类型分布
6. 最近 5 条探测摘要
7. 首次异常时间

---

## 15. 非目标

以下内容不属于本方案首期范围：

1. 判断模型是否为“官方同款”。
2. 判断模型是否被降级冒充。
3. 复杂知识题能力评测。
4. 价格真实性与扣费真实性校验。
5. 全球多地域网络观测。

这些能力后续可以在有效性自动测试稳定后，作为二期能力增加。

---

## 16. 验收标准

系统满足以下条件即可认为“中转站模型有效性自动测试方案”落地完成：

1. 能按固定调度周期自动探测站点模型。
2. 探测使用真实 Chat Completions 请求，而非伪检测。
3. HTTP 200 但无有效 delta 时，系统明确判定失败。
4. 系统能够区分 `UP / DEGRADED / DOWN`。
5. 系统能够记录首 token、总耗时、失败类型与响应摘要。
6. 系统支持补测，且连续 2 次失败才进入 `DOWN`。
7. 冷启动样本不足时，不输出误导性得分。
8. 敏感信息不落库，证据信息可回溯。

---

## 17. 实施建议

为避免过度设计，建议按以下顺序落地：

### 第一阶段

1. 真实流式请求探测。
2. 成功/失败判定。
3. 失败分类。
4. 状态机。

### 第二阶段

1. 5 分钟调度。
2. 补测队列。
3. 24h 聚合分。
4. 基础告警。

### 第三阶段

1. 协议异常细分。
2. 多渠道拆分。
3. 多出口代理探测。

这样可以先把“能否自动判定模型有效”做实，再逐步扩展复杂能力。

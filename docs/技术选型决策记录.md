## 3. 为什么这样选

## 3.1 为什么后端选原生 ASP.NET Core

1. 已明确要求 API 使用 `.NET`
2. 已明确确认保留原生 `ASP.NET Core`
3. 原生方案控制力强，适合中型数据产品
4. 不会提前绑定到重型业务框架

## 3.2 为什么 ORM 选 SqlSugar

1. 已明确要求改为 `SqlSugar`
2. `SqlSugar` 在国内 .NET 场景使用广泛
3. 对 MySQL 适配成熟
4. 统一一个 ORM，维护成本最低

## 3.3 为什么用户端选 Next.js 而不是 Vue / Nuxt

1. 已接受 `React` 或 `Vue`，未强制 Vue
2. 管理端已经确定走 `React + Ant Design Pro`
3. 为了统一前端生态，用户端也选 React 更稳
4. `Next.js` 是 React 下最成熟的 SEO 方案之一

不选 `Nuxt` 不是因为不能做，而是因为：

1. 会形成 React + Vue 双生态
2. 用户端和管理端之间难以共享前端规范、工具链和公共代码

## 3.4 为什么管理端选 Ant Design Pro 而不是 Blazor

1. 已明确要求优先成熟实现
2. 管理端是典型的数据密集型后台
3. `Ant Design Pro` 在后台场景的成熟度和交付效率更高

不选 `Blazor` 的原因：

1. 技术统一性强，但后台模板和生态不如 Ant Design Pro 成熟
2. 对当前项目，后台的成熟交付效率比全栈统一更重要

## 3.5 为什么任务调度选 Hangfire 而不是 Quartz

1. 当前项目不只是定时任务，还需要后台运维可见性
2. `Hangfire` 的后台面板更适合管理员使用
3. 抓取、测试、补测、风险重算都适合用 Hangfire 管理

不选 `Quartz` 的原因：

1. Quartz 更偏调度引擎
2. 当前项目更需要任务面板和运维感知

## 3.6 为什么访问方式选独立子域名

1. 用户端和管理端边界清晰
2. SEO 和后台天然隔离
3. 安全策略更容易控制
4. 部署和缓存策略更清晰

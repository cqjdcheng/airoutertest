## 5. 自助测试功能判断

### 5.1 使用意愿

| 使用意愿 | 占比 | 小计 |

结论：

1. 88.8% 的用户存在某种使用意愿，但多数不是高频使用。
2. 自助测试更适合作为诊断工具，不适合作为首期首页主入口。

### 5.2 最大顾虑

| 顾虑 | 占比 | 小计 |
|---|---:|---:|
| API 密钥安全 | 66.7% | 18 |
| 测试结果不可信 | 44.4% | 12 |
| 操作太复杂 | 29.6% | 8 |
| 怕平台保存我的信息 | 29.6% | 8 |
| 怕测试消耗额度 | 22.2% | 6 |
| 没这个需求 | 14.8% | 4 |

需求调整：

1. 自助测试上线前必须明确 Key 不落库、日志脱敏、仅一次性使用。
2. 页面必须明确测试会消耗用户额度。
3. 结果应展示测试过程、时间、错误类型和证据摘要，否则用户会质疑可信度。

## 7. 调整后的 MVP 建议

### 7.1 P0 首期必须做

1. 中转站基础收录和后台维护。
2. 模型维度价格排行，主排序使用实际折算价。
3. 模型维度稳定性排行，展示 24 小时和 7 天可用性、速度指标。
4. 平台定时测试，用统一测试口径生成公共排行。
5. 基础风险识别，优先覆盖模型偷换、降级冒充、成功率不稳定、价格虚标。
6. 精简站点详情页，用于承接价格、稳定性、风险证据和跳转链接。
7. 排行口径说明，明确数据更新时间、测试来源和计算规则。

### 7.2 P1 首期后半段或内测增强

1. 综合性价比排行。
2. 历史价格和稳定性趋势。
3. 用户自助测试的安全版本。
4. 中转站整体评分。
5. 风险证据详情和误报复核。

### 7.3 P2 后置功能

1. 第三方模型能力排行独立页。
2. 公开提交站点入口。
3. 企业筛选增强，包括开票、退款、文档、客服等筛选组合。
4. 文章系统、广告系统、会员体系。

---

## 8. 需求取舍结论

调整后的首期方向应是：

1. 以个人开发者和高频 API 用户为主，不以企业采购为主。
2. 以模型维度排行为主，不以站点大全为主。
3. 以实际折算价和稳定性为首屏核心，不以资讯、文章或导航为核心。
4. 以模型真实可用和防偷换、防降级作为可信基础，不把反造假只做成独立卖点。
5. 以平台定时测试作为公共数据来源，自助测试作为低频诊断工具。
6. 以可解释数据赢得信任，所有排行必须展示更新时间、测试口径和关键证据。

# AI 中转站模型测试方案

## 1. 文档目标

本文档用于定义 AI 中转比价网中的模型测试体系，覆盖以下内容：

1. 需要测试哪些维度
2. 每个维度如何测试
3. 背后的实现原理
4. 技术实现方案
5. 可参考的开源仓库

本文档主要服务于以下需求：

1. 为前台提供价格、速度、稳定性、风险等可展示数据
2. 为后台提供自动化测试、补测、复核和告警能力
3. 为排行榜、综合评分和反造假体系提供可靠输入

---

## 2. 测试体系的总体原则

## 2.1 只用真实请求，不用假请求

测试必须针对真实中转站、真实 API 地址、真实模型名发起请求。

原因：

1. 模拟请求无法发现真实链路中的限流、上游切换、缓存、偷换模型、扣费异常
2. 用户真正关心的是“我充钱以后是否能正常用”

---

## 2.2 平台定时测试与用户自助测试分开

建议把测试分成两类：

1. 平台定时测试
2. 用户自助测试

区别：

1. 平台定时测试用于：
   - 公共排行
   - 稳定性分析
   - 风险分析
   - 历史统计

2. 用户自助测试用于：
   - 帮单个用户验证某个站点
   - 不进入公共排行

原因：

1. 用户自助测试参数不可控
2. 用户自助测试数据不稳定
3. 公共排行必须基于统一测试口径

---

## 2.3 所有测试必须留证据

不能只存“通过 / 失败”。

至少需要保留：

1. 请求时间
2. 目标站点
3. 模型名称
4. 首 token 时间
5. 完整响应耗时
6. 错误类型
7. 响应摘要
8. 风险命中记录
9. 测试配置版本

原因：

1. 风险结论需要可回放
2. 前台展示需要可解释
3. 后台误报复核需要原始证据

---

## 2.4 不能单次判定，必须多次复测

任何造假、降级、速度异常、稳定性问题，都不应依赖单次测试直接定性。

建议：

1. 首次命中风险后，自动加入补测队列
2. 在不同时间段重复测试
3. 只有连续命中或高概率命中时，才升级风险等级

---

## 3. 需要测试的维度

建议测试维度分为 6 类：

1. 连通性测试
2. 响应速度测试
3. 可用性测试
4. 稳定性测试
5. 价格与计费测试
6. 反造假测试

---

## 4. 连通性测试

## 4.1 测试目标

确认站点是否至少具备基础调用能力。

## 4.2 测试方法

建议分为两步：

1. 基础接口连通测试
2. 最小模型调用测试

### 基础接口连通测试

测试项：

1. 域名是否可访问
2. HTTPS 是否正常
3. OpenAI 兼容接口是否可连接

### 最小模型调用测试

测试项：

1. 指定模型是否可被调用
2. 返回结构是否符合预期
3. 是否能拿到基本 usage / message 数据

## 4.3 实现原理

本质是验证：

1. 站点链路是否存活
2. 模型路由是否存在
3. 返回结构是否符合兼容协议

## 4.4 结果字段

建议记录：

1. `connect_success`
2. `http_status`
3. `protocol_ok`
4. `model_exists`
5. `error_type`

---

## 5. 响应速度测试

## 5.1 测试目标

衡量模型是否“快”，并区分：

1. 首 token 快不快
2. 完整响应快不快

## 5.2 核心指标

建议至少记录 4 个指标：

1. `dns_connect_time`
2. `ttfb`
3. `first_token_time`
4. `full_response_time`

其中前台核心展示建议用：

1. 首 token 时间
2. 完整响应耗时

## 5.3 测试方法

### 流式响应场景

1. 记录发起请求时间
2. 记录收到第一个 token 的时间
3. 记录最后一个 token 到达时间

### 非流式响应场景

1. 记录请求发起时间
2. 记录完整响应返回时间

### 建议测试输入

不要用太长或太复杂的任务，避免能力差异过度干扰速度结果。

建议使用：

1. 短指令
2. 固定上下文长度
3. 固定输出长度上限

## 5.4 实现原理

速度不是只看单个 HTTP 请求耗时。

真正有意义的是：

1. 用户多久看到第一个输出
2. 用户多久拿到完整结果

因此建议优先测试流式输出时间，而不是只测整包返回时间。

## 5.5 展示建议

前台可展示：

1. 首 token 平均值
2. 首 token P95
3. 完整响应平均值
4. 完整响应 P95

---

## 6. 可用性测试

## 6.1 测试目标

衡量“这个模型在这个站点上经常能不能成功调用”。

## 6.2 测试方法

建议平台对每个站点-模型组合按小时定时测试。

每次测试记录：

1. 成功 / 失败
2. 错误类型
3. 耗时
4. 风险命中

## 6.3 计算方式

建议定义：

`availability = 成功次数 / 总测试次数`

建议按以下窗口聚合：

1. 24h
2. 7d
3. 30d

## 6.4 错误类型分类

建议统一错误类型，至少包括：

1. 连接失败
2. TLS/证书错误
3. 认证失败
4. 模型不存在
5. 限流
6. 超时
7. 上游错误
8. 响应格式异常

---

## 7. 稳定性测试

## 7.1 测试目标

衡量“这个站点不是偶尔能用，而是持续稳定”。

## 7.2 为什么不能只看成功率

两个站点都可能是 `98%` 成功率，但体验完全不同：

1. 一个站点全天都比较平稳
2. 一个站点白天经常抖动，晚上又恢复

所以稳定性必须同时考虑：

1. 成功率
2. 速度波动
3. 不同时段波动

## 7.3 测试方法

建议每小时定时测，形成时间序列。

对每个站点-模型组合，统计：

1. 24h 成功率
2. 7d 成功率
3. 30d 成功率
4. 首 token 时间标准差
5. 完整响应耗时标准差
6. 错误类型分布

## 7.4 建议评分公式

先定义：

1. `availability_rate = success_count / total_count`
2. `ft_cv = std(first_token_time) / mean(first_token_time)`
3. `rt_cv = std(full_response_time) / mean(full_response_time)`

然后：

1. `ft_stability = 1 - min(ft_cv, 1)`
2. `rt_stability = 1 - min(rt_cv, 1)`

最终：

`stability_score = 100 * (0.6 * availability_rate + 0.2 * ft_stability + 0.2 * rt_stability)`

## 7.5 展示建议

前台建议展示：

1. 24h 稳定性
2. 7d 稳定性
3. 30d 稳定性
4. 趋势图

---

## 8. 价格与计费测试

## 8.1 测试目标

确认用户看到的价格和用户实际付出的成本是否一致。

## 8.2 测试内容

建议测试两部分：

1. 展示价格是否真实
2. 实际扣费是否真实

## 8.3 测试方法

### 价格抓取

从站点页面或兼容接口中抓取：

1. 模型标价
2. 标价币种
3. 充值比例
4. 活动赠送

### 扣费校验

在内部测试账号场景下：

1. 记录调用前余额
2. 发起已知成本的标准请求
3. 记录调用后余额
4. 计算实际扣费

## 8.4 实现原理

一个站可能：

1. 标价很低
2. 但充值比例不利
3. 或赠送规则复杂
4. 或实际扣费与标价不一致

所以前台比价不能只展示标价，必须展示实际折算价。

## 8.5 实际折算价公式

定义：

1. `paid_amount_local`
2. `fx_rate`
3. `usable_credit`
4. `site_unit_price`

计算：

1. `paid_amount_usd = paid_amount_local / fx_rate`
2. `cost_per_credit_usd = paid_amount_usd / usable_credit`
3. `effective_price_usd = site_unit_price * cost_per_credit_usd`

---

## 9. 反造假测试

## 9.1 测试目标

识别以下造假或掺水行为：

1. 缓存假响应
2. 模型偷换
3. 降级模型冒充高阶模型
4. 价格虚标
5. 响应伪造
6. 上游 / 号池异常波动
7. 隐藏 prompt 注入导致额外扣费

---

## 9.2 缓存假响应测试

### 测试思路

使用理论上应该产生不同结果的问题进行重复请求。

### 测试方法

1. 设计带随机种子的数学题
2. 设计带 nonce 的结构化输出题
3. 短时间内重复调用 2-5 次
4. 比较输出是否异常一致

### 风险信号

1. 理论应变化的输出完全不变
2. 长回答却异常快
3. token 使用异常稳定

### 结果建议

命中后建议加分：

`+15 ~ +30`

---

## 9.3 模型偷换测试

### 测试思路

不同模型在回答风格、结构、推理方式和代码习惯上存在行为指纹。

### 测试方法

1. 为每个目标模型准备一组标准探测题
2. 记录回答文本、结构和关键行为特征
3. 与目标模型基线做相似度比对

### 可用特征

1. 结构化回答格式
2. 代码风格
3. 数学推理路径
4. 工具调用习惯
5. 长上下文摘要风格

### 风险信号

1. 长期更像另一个低阶模型
2. 输出特征与目标模型差异过大

### 结果建议

命中后建议加分：

`+20 ~ +40`

---

## 9.4 降级模型冒充高阶模型测试

### 测试思路

目标不是判断“像不像某模型”，而是判断“是不是明显低于这个应有档次”。

### 测试方法

建议准备一组高区分度题目：

1. 高难推理题
2. 代码修复题
3. 长上下文抽取题
4. 严格结构化输出题

然后：

1. 多轮请求
2. 和高阶模型基线比对
3. 若长期明显偏低，则提升风险

### 风险信号

1. 回答质量稳定落在低阶模型水平
2. 推理结构明显缩水
3. 工具型或代码型题目退化明显

### 结果建议

命中后建议加分：

`+25 ~ +45`

---

## 9.5 隐藏 Prompt 注入 / 额外扣费测试

### 测试思路

部分中转站可能通过偷偷注入 prompt，导致 input tokens 虚增。

### 测试方法

1. 发起极短请求，例如简单问候或固定短句
2. 记录返回的 usage / input tokens
3. 和理论 token 成本对比
4. 多次重复验证

### 风险信号

1. 超短请求却长期出现异常高输入 token
2. 不同请求输入 token 固定偏高

### 结果建议

命中后建议加分：

`+15 ~ +35`

---

## 9.6 响应伪造测试

### 测试思路

检查返回结构、usage、streaming chunk、finish reason 等是否合理。

### 测试方法

1. 检查响应结构是否符合兼容协议
2. 检查 usage 是否长期固定得不合理
3. 检查内容长度与响应耗时是否匹配
4. 检查流式 chunk 是否自然

### 风险信号

1. usage 值异常模式化
2. stream chunk 结构异常
3. 长文本瞬间整包返回
4. response 内容存在明显模板拼接痕迹

### 结果建议

命中后建议加分：

`+15 ~ +35`

---

## 9.7 上游 / 号池不稳定测试

### 测试思路

即使模型没造假，号池切换频繁、上游抖动也会严重影响体验。

### 测试方法

1. 按小时定时测
2. 在高峰和低峰时段重复测
3. 比较速度、成功率和错误类型变化

### 风险信号

1. 同一模型延迟波动极大
2. 成功率阶段性明显下降
3. 路由特征频繁切换

### 结果建议

命中后建议加分：

`+10 ~ +25`

---

## 10. 风险分设计

## 10.1 总体原则

风险分要可解释，不能是黑箱。

建议：

`risk_score = min(100, 所有命中规则分数累加)`

## 10.2 分段建议

1. `0-20`
   - 低风险
2. `21-50`
   - 中风险
3. `51-80`
   - 高风险
4. `81-100`
   - 严重可疑

## 10.3 展示方式

前台：

1. 状态标签
2. 风险分
3. 证据摘要

详情页：

1. 命中的规则
2. 最近一次命中时间
3. 证据记录

后台：

1. 风险命中列表
2. 证据明细
3. 补测入口
4. 误报标记

---

## 11. 技术实现方案

## 11.1 整体架构

建议拆成 5 层：

1. Web 前端
2. API 服务
3. 调度与队列
4. 测试 / 抓取 / 风险 Worker
5. 数据与证据存储

---

## 11.2 组件划分

### 前端

负责：

1. 展示速度、稳定性、风险、排行
2. 展示测试结果
3. 提供自助测试入口

### API 服务

负责：

1. 提供站点、模型、排行、测试、风险接口
2. 提供后台管理接口
3. 接收用户自助测试请求

### Scheduler

负责：

1. 按小时创建价格抓取任务
2. 按小时创建平台测试任务
3. 按日创建第三方榜单同步任务
4. 在命中风险后创建补测任务

### Test Worker

负责：

1. 发起真实 API 请求
2. 记录速度和可用性
3. 保存响应摘要

### Risk Worker

负责：

1. 读取测试结果
2. 执行反造假规则
3. 输出风险分和证据

### Crawl Worker

负责：

1. 抓取站点价格
2. 解析充值比例和赠送活动
3. 生成标准化价格数据

---

## 11.3 推荐技术栈

建议方案：

### 前端

1. `Next.js App Router`
2. `React`
3. `TypeScript`
4. `ECharts`

### 后端

1. `.NET 10 LTS`
2. `ASP.NET Core Web API`
3. `SqlSugar`
4. `MySQL 8.4 LTS`
5. `Redis 7+`
6. `Hangfire`

### 抓取与测试

1. `Playwright`
2. `HTTP client`
3. 独立 `.NET Background Job` 进程

### 存储

1. `MySQL`
   - 结构化数据
2. `Object Storage`
   - 抓取快照、证据原文、测试样本

---

## 11.4 数据流

### 平台定时测试链路

1. Scheduler 创建站点-模型测试任务
2. Test Worker 发起真实请求
3. 写入 `test_records`
4. Risk Worker 读取测试记录并执行规则
5. 写入 `risk_evidences` 和风险分
6. 聚合服务刷新可用性、稳定性、排行结果
7. 前台读取聚合结果展示

### 用户自助测试链路

1. 用户提交站点地址、Key、模型名
2. API 创建临时测试任务
3. Test Worker 执行
4. Risk Worker 分析
5. 结果只返回给当前用户
6. 默认不写入公共排行聚合

---

## 11.5 存储建议

建议至少有以下核心表：

1. `relay_sites`
2. `models`
3. `channels`
4. `relay_offers`
5. `test_records`
6. `risk_evidences`
7. `site_rankings`
8. `model_rankings`
9. `crawl_jobs`
10. `test_jobs`
11. `Hangfire` 任务持久化表

建议单独存储：

1. 抓取原始快照
2. 测试原始响应摘要
3. 风险命中证据

---

## 11.6 任务调度建议

### 每小时

1. 价格抓取
2. 平台定时测试
3. 风险重算
4. 排行刷新

### 每天

1. 第三方模型能力榜同步
2. 历史数据归档
3. 站点资料完整度检查

### 手动

1. 补测
2. 价格重抓
3. 风险重算
4. 审核通过后初始化任务

---

## 12. 开源仓库参考

以下仓库适合纳入实现参考，但不要直接照搬，应该按你的业务目标拆分吸收。

## 12.1 RelayRadar

- 仓库地址：
  - https://github.com/AetherCore-Dev/relay-radar

### 适用场景

1. 中转站真假检测
2. 模型偷换 / 降级检测
3. 隐藏 prompt / 额外扣费检测
4. 中转站综合评分思路

### 值得借鉴的点

1. `monitor`
   - 监控型检测思路
2. `verify`
   - 主动探测型检测思路
3. `probe`
   - 延迟测试
4. `rank`
   - 多维评分

### 注意

1. 它更偏检测和排名，不是完整的站点管理平台
2. 需要结合你自己的数据库、后台和公开前台展示体系

## 12.2 One Tracker

- 仓库地址：
  - https://github.com/NekroAI/one-tracker

### 适用场景

1. 多站点价格聚合
2. 价格标准化
3. 充值比例折算

### 值得借鉴的点

1. 多供应商解析器设计

### 注意

## 12.3 lm-evaluation-harness

  - https://github.com/EleutherAI/lm-evaluation-harness

### 适用场景

1. 标准模型能力评测

3. 自定义评估任务

### 值得借鉴的点

1. 统一评测框架设计

### 注意

## 15. 当前结论

这个项目的模型测试体系，不能只做“延迟测试”，也不能只做“模型能力评测”。

真正需要的是一套组合方案：

1. 用真实请求测试连通性、速度和可用性
2. 用时间序列统计稳定性
3. 用价格抓取和扣费校验做价格真实性判断
4. 用探测题、行为特征和重复测试做反造假
5. 用规则引擎输出风险分和证据

如果只做其中一部分，这个平台会退化成普通比价站或普通测速站。

如果把这 5 类能力都做起来，才会形成真正的产品壁垒。
